1. 첫 빌드를 성공시킵니다

저장소 루트에서 명령을 실행합니다. core는 게임 규칙·화면·파일 접근, engine은 범용 AST 실행·경로 탐색·글자 공개·그래픽 계산을 담당합니다. content는 인물·장비·책략·스킬의 YAML 작성 원본입니다. desktop/android는 실행 진입점이며 verification은 검증 모듈입니다.

  1. Git, JDK 17 이상과 프로젝트 Gradle 래퍼를 준비합니다. Gradle 실행 JVM의 요구 버전도 래퍼 버전과 맞춥니다. 현재 Kotlin/Java 게임 코드 타깃은 JVM 17입니다.
  2. 전체 게임 빌드에는 Python 3, Node.js, 복원 자산 프로젝트가 필요합니다. Android 컴파일에는 SDK가 필요합니다. 기존 외부 프로젝트는 Electron 등 자산 생성 도구 의존성도 설치되어 있어야 합니다.
  3. core/build.gradle.kts의 restoredScenarioDirectory, cocosAssetsDirectory를 확인합니다. 시나리오 입력은 저장소의 content/scenarios이며 자산 입력은 현재 /Users/ain/workspace/jojo_mobile/sgccz-desktop/assets 절대 경로입니다. 다른 컴퓨터에서는 자산 입력을 실제 복원 프로젝트 경로로 변경해야 합니다. 이 저장소만 clone하면 전체 게임 자산까지 준비되는 구조는 아닙니다.
  4. 먼저 외부 자산 없이 가능한 YAML 컴파일을 실행한 뒤 전체 리소스 빌드로 진행합니다.
cd /Users/ain/workspace/jojo
java -version
python3 --version
node --version
./gradlew :core:compileGameContent
./gradlew :core:processResources
./gradlew :desktop:run --args="--scenario=R_01"

성공 기준: 첫 명령은 BUILD SUCCESSFUL과 core/build/generated/game-content/data/*.bin 생성을 확인합니다. 리소스 빌드는 생성 표를 core/build/resources/main/maps/data/에 포함합니다. 데스크톱 실행은 창을 열어 R_01 장면을 표시합니다. 전체 게임이 실패했더라도 YAML 컴파일 성공 여부와 외부 자산 오류를 구분하세요.

2. 파일이 게임에 도달하는 경로

content/의 개별 YAML
개발자가 수정하고 Git으로 관리
↓ :core:compileGameContent
스키마·ID·타입·스킬 참조 검사
기존 형식의 여섯 테이블 생성
↓ :core:processResources
maps/data/*.bin 번들
GameDataRepository → GameDataCatalog → 게임 규칙·화면

실행 중 파일을 자동 재로딩하는 기능은 없습니다. YAML 수정 후 빌드하고 게임을 다시 시작합니다. .bin과 build/resources는 생성물이므로 직접 편집하지 않습니다. 같은 여섯 외부 테이블은 번들에서 제외됩니다. YAML 파서는 buildSrc에만 있으며 게임 실행 시 YAML을 직접 해석하지 않습니다.

대사 확인·글자 공개·자동 진행은 전투·거리·궁전 모두 RuntimeDialogueSessionAdapter와 DialogueSession을 사용합니다. 배치와 타이밍 정책은 장면별 설정입니다. 새 장면마다 별도의 대화 타이머를 만들 필요가 없습니다.

3. YAML을 처음 작성할 때

YAML 파일 하나는 요소 하나입니다. id가 식별자이며 파일명은 정렬·탐색을 위한 관례입니다. 같은 디렉토리의 ID는 0부터 연속되어야 합니다. 기존 ID를 바꾸거나 삭제하면 저장 데이터·스크립트 참조가 달라집니다.

# 올바른 작성 예
id: 0
name: "조조"
attack: 41
intro: |
  첫 번째 줄입니다.
  두 번째 줄입니다.
# 정수 플래그는 true가 아닌 0 또는 1 등 기존 코드 값을 사용
famous: 1
  • 들여쓰기는 공백을 사용합니다. 탭은 사용하지 않습니다. 동일한 수준의 키는 같은 들여쓰기를 유지합니다.
  • 문자열은 따옴표로 감싸면 콜론, #, yes/no 같은 값이 다른 타입으로 해석되는 것을 피할 수 있습니다. 여러 줄 문장은 |로 쓸 수 있으며 끝 줄바꿈도 값에 들어갑니다.
  • 정수는 41입니다. "41"은 문자열, 41.0은 소수이므로 integer 필드에서 실패합니다.
  • 목록은 [106, 107] 또는 줄별 - 106 형태를 사용합니다. 목록 순서가 데이터 의미에 영향을 줄 수 있으므로 임의 정렬하지 않습니다.
  • 선택 필드 생략은 기존 게임 기본값을 사용한다는 뜻입니다. 생략·0·빈 문자열은 서로 다릅니다. null로 빈 필드를 만들지 않습니다.
  • 키 중복은 오류입니다. YAML 별칭/앵커를 통한 컬렉션 재사용은 현재 컴파일러에서 지원하지 않습니다. 요소마다 값을 명시합니다.
  • content/schema.json에 없는 필드 이름은 오류입니다. 새 키를 스키마에 등록하는 것만으로 새 전투 효과가 구현되지는 않습니다.
# skills/active의 병종별 습득 레벨
learnLevels:
  "24": 1
  "25": 5
# 숫자로 보이는 키도 따옴표를 붙인 문자열이어야 합니다.

기존 테이블 문구에는 ReviewedKoreanText 번역 처리가 적용됩니다. YAML의 기존 문구와 일치하는 번역 키가 있으면 검수 번역이 표시됩니다. 문구를 바꿨는데 표시가 예상과 다르면 localization의 키와 패치를 함께 확인합니다.

4. 무엇을 어느 디렉토리에 작성하나요?

디렉토리내용현재 ID 범위
characters인물 기본 정보·능력·자산 참조0~511
equipment장비·소비 아이템과 기존 효과 그룹 연결0~255
skills/active능동 책략과 습득 조건0~142
skills/passive패시브 효과의 이름·합성/표시 메타데이터0~333
skills/assignments패시브를 인물·병종에 배정0~156
skills/equipment장비 효과의 패시브 ID·수치·성장 규칙0~251

범위는 이 문서 작성 시점입니다. 복사 전에 현재 마지막 파일과 YAML의 ID를 확인합니다. 장비 ID 150~254는 일부 경로에서 소비 아이템으로 분류되고, 255는 미지정 표식으로 쓰입니다. 255 이상의 장비에는 compact ID 변환도 있습니다. 장비는 다음 번호를 추가했다고 모든 획득·장착 경로가 자동 지원되지는 않습니다.

5. 첫 실습: 조조의 공격 수치를 바꿉니다

  1. content/characters/0000.yaml을 엽니다. attack: 41을 attack: 45로 변경합니다. ID와 다른 키는 유지합니다.
  2. 아래 명령으로 YAML 검증과 리소스 생성을 실행합니다.
./gradlew :core:compileGameContent :core:processResources

수치가 실제 런타임 카탈로그에 들어갔는지 확인하려면 아래 파일을 core/src/test/kotlin/com/jojo/game/ContentAuthoringSmokeTest.kt로 작성합니다. 이 테스트는 본 실습 변경을 적용한 상태에서 통과하도록 작성된 예입니다.

package com.jojo.game

import com.jojo.game.infrastructure.data.GameDataCatalog
import kotlin.test.Test
import kotlin.test.assertEquals

class ContentAuthoringSmokeTest {
    @Test fun authoredAttackIsLoaded() {
        val catalog = GameDataCatalog.load()
        assertEquals(45, catalog.unitProfile(0)?.attack)
    }
}
./gradlew :core:test --tests 'com.jojo.game.ContentAuthoringSmokeTest'
./gradlew :desktop:run --args="--scenario=R_01"

성공 기준: 위 테스트가 통과하면 YAML → 생성물 → 런타임 조회 연결이 확인된 것입니다. 화면의 최종 전투 능력은 레벨·병종·장비·캠페인 상태로 다시 계산될 수 있어 표시값이 그대로 45일 필요는 없습니다. 실습을 끝내고 원래 값을 유지하려면 attack을 41로 돌리고 테스트 기대값도 함께 수정하거나 실습 테스트를 제거합니다.

6. 새 인물을 등록하고 장면에 배치합니다

  1. 현재 인물의 마지막 ID가 511인지 확인합니다. 그렇다면 content/characters/0512.yaml을 다음과 같이 작성합니다. 기존 자산 참조를 재사용하는 실습이므로 새 이미지 준비 없이 카탈로그 등록을 확인할 수 있습니다.
id: 512
name: "신규 장수"
face: 0
mapAvatar: 0
speechGroup: 0
attack: 41

critical: 40

  1. :core:compileGameContent로 검증합니다. 앞 절 테스트에 assertEquals("신규 장수", catalog.unitProfile(512)?.name)를 추가하고 통과를 확인합니다.
  2. 캠페인에 합류시키려면 R 시나리오의 실행되는 함수에 model.unitJoin(512)를 연결합니다. 거리 출현은 별도로 stage.showUnits([[512, 52, 41, 2]])를 사용합니다. 이 좌표는 기존 R_01 배경 호출 형태를 기준으로 한 예이며 실제 지도에서 보이는 위치를 확인해야 합니다.
  3. 새 화자 대사는 stage.say('&512\n주군, 명을 내려주십시오.')로 작성하고, 다음 절의 대사 카탈로그 등록도 수행합니다.
  4. 실행 후 인물 표시·초상화·합류 목록과 저장/불러오기를 확인합니다. 전투 배치는 S 시나리오에 별도로 연결합니다. YAML의 인물 등록만으로 새 전투 부대가 자동 생성되지는 않습니다.

새 초상화·거리/전투 외형은 face/mapAvatar/battleAvatar에 대응하는 자산 내보내기가 필요합니다. 숫자를 새로 지정하는 것만으로 이미지가 생성되지는 않습니다.

7. 대사·거리·궁전·전투 연결

시나리오 Python은 현재 저장소의 content/scenarios에 있습니다. R_01 등 기존 모듈을 백업한 뒤 실행되는 scene 함수 안에 짧은 변경을 넣어 확인합니다. 함수 이름만 추가하면 현재 장면에서 호출되지 않을 수 있으므로 자연 순서(scene0→scene1)와 메뉴·점프 조건을 확인합니다.

# 기존 scene 함수 안에서의 호출 예 (새 인물 512 등록 후)
model.unitJoin(512)
stage.showUnits([[512, 52, 41, 2]])
stage.draw()
stage.say('&512\n주군, 명을 내려주십시오.')
  1. ./gradlew :core:exportScenarioAst를 실행합니다.
  2. core/build/generated/scenario-ast/R_01.json에서 새 호출의 @dialogue:R_01:sceneN:줄번호를 확인합니다. 번호를 추측하지 마세요.
  3. content/scenarios/dialogue-text.json의 entries에 실제 생성 키를 넣습니다. 예를 들어 실제 키가 R_01:scene1:60이라면 아래처럼 추가합니다. JSON의 기존 항목과 쉼표를 유지해야 합니다.
"R_01:scene1:60": "&512\n주군, 명을 내려주십시오."

위 60은 설명용입니다. 키가 없으면 Unknown scenario dialogue text key 오류가 납니다. 줄을 삽입하면 다른 대사의 키도 바뀌므로 기존 키와 문장 대응도 점검합니다.

  1. :core:processResources 후 :desktop:run --args="--scenario=R_01"으로 확인합니다. 첫 확인은 남은 글자를 공개하고, 다음 확인은 대사를 진행해야 합니다.
  2. 새 R/S 모듈이면 content/scenarios/manifest.json에도 기존 형식을 따라 등록합니다. exporter는 AST만 생성하고 manifest와 대사 카탈로그를 자동 갱신하지 않습니다.
  3. 새 전투는 기존 S 모듈의 scene0 초기화·부대/맵/승리 조건, scene1 턴 이벤트, scene2 종료/보상, __dispatch__ 계약을 함께 확인합니다. R_XX가 같은 번호 S_XX를 찾으며 없으면 S_00으로 가는 경로가 있으므로 대상 모듈을 확인합니다.

전투·지도·아이템·책략별 구현 경로는 기능별 가이드의 전투 절에 연결되어 있습니다. 완전한 새 전투는 기존 맵·부대를 복제한 작은 전투부터 시작해 첫 턴 → 승리 → 패배 → 복귀를 각각 확인합니다.

8. 장비 수치와 스킬을 연결합니다

수치 변경 실습: content/equipment/0070.yaml(가죽 갑옷)의 value: 10을 12로 바꿉니다. 컴파일 후 카탈로그 테스트에서 assertEquals(12, catalog.equipmentProfile(70)?.value)로 확인합니다. 실제 장비창에서는 장비 레벨 등의 보정이 포함됩니다.

skillEffects는 현재 효과 그룹 연결입니다.

컴파일러는 equipment/{id}.yaml에 적힌 skillEffects를 itemSkills.index의 해당 id 그룹에 저장합니다. 게임은 일반 특수 장비의 specialType, 보조구(itemType > 60)의 itemType으로 그룹을 조회합니다. 일반 장비 중 짝수 itemType은 이 효과 경로에서 제외됩니다. 따라서 파일 안에 skillEffects를 넣는 것만으로 그 파일의 장비에 자동 부착된다고 생각하면 안 됩니다.

equipment/0090.yaml 봉황 깃옷
itemType: 23 · specialType: 26 · effectValue: 20
↓ 그룹 26 조회
equipment/0026.yaml
skillEffects: [106]
↓ 효과 106 조회
skills/equipment/0106.yaml
skillId: 146 · phase: 1
↓ 패시브 효과
skills/passive/0146.yaml
매 턴 HP 회복

봉황 깃옷의 회복 효과 값을 25로 바꾸려면 우선 equipment/0090.yaml의 effectValue를 25로 수정합니다. 효과 106에 별도 effectValue가 있으면 그 값이 우선하므로 해당 파일도 확인합니다. phase:1은 높은 장비 레벨에서 수치에 영향을 주므로 최종값 검증은 낮은 레벨과 높은 레벨을 나누어 수행합니다. 같은 그룹을 쓰는 다른 장비에도 영향이 있는지 확인합니다.

기존 그룹 연결 보존을 위해 이 저장 구조를 유지하고 있습니다. 새 장비를 추가할 때는 ID 범위·compact 변환·장착 조건·획득·상점·저장을 함께 다뤄야 하므로 먼저 기존 장비 수정 실습으로 경로를 익히세요.

9. 책략과 인물 패시브 작성 예

책략 수치 변경: skills/active/0000.yaml의 작열에서 mpCost를 6→4로 변경하고 다른 필드는 유지합니다. 기존 effect/category를 재사용하므로 새 효과 코드를 만들 필요가 없습니다. 병종별 습득은 learnLevels에 정의하며 이미 사용 가능한 인물로 비용 차감을 확인합니다. 새로운 ID를 추가할 때는 현재 마지막 142 다음인 143을 사용하고 전체 기존 항목을 복사한 뒤 이름·수치·습득을 수정합니다. 실제 마지막 ID가 달라졌다면 그 다음 번호를 사용합니다.

인물 패시브 추가: 현재 배정의 마지막 ID가 156이라면 다음 파일을 content/skills/assignments/0157.yaml로 작성합니다. 기존 효과 146을 인물 0(조조)에 배정하는 예입니다.

index: 157

posts를 생략하면 기존 기본값을 사용하며 unit0로 지정한 인물 배정을 확인합니다. 같은 효과가 기존 병종·장비에도 있으면 합성 규칙에 따라 최종값이 달라집니다. 인물별 스킬 목록, 턴 시작 시점의 HP 변화, 중독 등 다른 상태와의 적용 순서를 확인합니다. 이름과 intro를 쓰는 것만으로 새 효과가 만들어지는 것은 아닙니다.

완전히 새로운 효과: skills/passive에 새 정의를 추가해도 해당 ID를 처리하는 core 규칙이 없으면 원하는 행동이 생기지 않습니다. GameDataCatalogCombatDomain의 passiveAbility/mergeSkills와 실제 전투 소비 지점을 구현하고 테스트합니다. 능동 책략은 MagicResolver·MagicDamageCalculator·대상/AI·연출까지 연결합니다. 이를 engine에 특정 스킬 ID 분기로 넣지 않습니다.

10. YAML 필드 전체 참조

인물: name은 이름, face/mapAvatar/battleAvatar는 초상화·거리·전투 자산 번호, posts는 병종/관직 참조, level은 레벨입니다. attack/defense/spirit/critical/morale은 현재 UnitProfile 이름으로 노출하는 기본 능력값이며 최종 전투 능력과 다를 수 있습니다. maxHitPoints/maxMagicPoints는 HP·MP 기초값입니다. speechGroup은 치명타 대사 그룹, criticalTexts는 개별 대사 목록, intro는 인물 소개입니다.

아이템: itemType은 장비 종류 코드, specialType은 특수 효과 그룹 조회 키, price는 가격, iconIndex는 원본 아이콘 번호입니다(화면 프로필은 +1). value는 기본 효과 수치, effectValue는 특수 효과 기본 수치, upgradeValue는 기존 8번 필드의 성장/병과 호환 값입니다. arms는 병과 관련 목록이고 treasure는 보물 플래그입니다. 수치 코드의 의미는 기존 같은 종류 항목과 GameDataCatalogEquipmentDomain의 소비 지점을 함께 확인합니다.

책략: type/target/category/harmType은 종류·대상·효과 분류 코드, hitArea/effectArea는 사거리·효과 범위 표 ID입니다. mpCost는 MP 비용, power는 위력, condition은 사용 조건, aiUse는 AI 사용 설정, hitRateLimit은 명중 제한 설정입니다. icon/effect는 아이콘·연출 자산 참조입니다. learnLevels는 병종별 습득 레벨입니다.

패시브: format은 설명 표시 방식, incrementType은 같은 효과의 합성 방식, argument는 효과 해석 인자, resetType은 기존 리셋 메타데이터입니다. 숫자를 임의로 바꾸어 새로운 행동을 만들 수 없습니다. 배정의 index는 기존 행 메타데이터, skillId는 효과 정의, value는 배정 수치, posts/unit0~2는 대상입니다.

장비 효과: effectValue를 지정하면 아이템의 기본 효과값보다 우선합니다. phase는 비트 플래그로 2=레벨 곱, 4=레벨 더하기, 8=(레벨+1) 곱, 64=레벨/2 더하기, 256=인물 레벨 더하기입니다. 32는 장비 레벨 6 이하에서 효과를 건너뛰고, 1과 128은 레벨 6 초과에서 각각 50% 증가·1 증가를 적용합니다. 여러 비트를 조합하면 코드 순서대로 연산되므로 기존 효과를 복사한 뒤 경계 레벨에서 검증하세요. upgrade는 레벨 6 초과에서 사용할 다른 패시브 ID입니다.

아래 표는 현재 content/schema.json에서 추출한 전체 필드입니다. id는 모든 YAML의 필수 정수입니다. 정수 코드는 기존 항목과 소비 코드를 확인해 선택하세요. 스키마의 필수 여부는 문법 검사의 최소 조건이며, 완전한 기능 구성에 필요한 모든 조건을 뜻하지는 않습니다.
