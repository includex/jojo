화살표는 코드의 의존 방향입니다. 런처는 게임을 시작하고, 게임은 엔진을 사용합니다. 모듈을 눌러 실제 역할을 확인하세요.

게임이 엔진을 호출합니다. core는 api(project(":engine"))로 엔진 타입을 노출하므로 런처와 검증 모듈도 core를 통해 엔진 API를 사용할 수 있습니다.

엔진도 LibGDX 공통 API에 의존합니다. 스크립트는 JsonValue, 그래픽은 Batch·TextureRegion을 사용합니다. 플랫폼 백엔드와 네이티브 라이브러리 구성은 desktop/android에 있습니다.

03

실제로 경계를 오가는 순간

코드의 의존 방향은 게임 → 엔진입니다. 실행 중에는 엔진이 주입받은 콜백을 호출하여 게임의 처리를 요청할 수 있습니다. 콜백 호출이 역방향 모듈 의존을 뜻하지는 않습니다.

예: 시나리오를 읽고 진행하다가 stage.choice를 만나면 어떻게 될까요?

1
게임이 시나리오를 선택하고 AST를 읽습니다.

ScenarioLoader가 scenario-ast/모듈명.json을 읽어 함수·레이블 정보를 구성합니다. 캠페인 상태와 실행할 함수의 선택도 게임의 일입니다.

2
게임이 변수와 호출 처리를 연결합니다.

ScenarioCallCoordinator가 vars/gvars/pvars와 전역 변수를 엔진에 바인딩하고, 호출 AST를 처리할 함수를 제공합니다.

3
엔진이 문장과 표현식을 실행합니다.

StatementExecutor가 프레임 커서를 진행하고 ExpressionEvaluator가 값을 계산합니다. ScriptCallStack은 호출·레이블 점프를 관리합니다.

4
게임이 선택지를 가로채고 UI를 엽니다.

ScenarioChoiceCoordinator.interceptStatement가 선택지 대입과 질문 분기를 처리합니다. 상태가 CHOICE로 바뀌면 게임의 shouldYield 조건에 따라 엔진 실행이 멈춥니다.

5
입력을 확정하고 같은 실행 흐름을 재개합니다.

게임이 결과를 반영한 뒤 인터프리터를 재개합니다. 엔진에 남아 있는 프레임과 커서가 이어서 실행됩니다.

CONTRACT

게임 이름을 모르는 실행기

엔진은 PlaybackState나 선택지 UI 타입을 참조하지 않습니다. 중단 여부와 게임 전용 문장의 처리를 콜백으로 받습니다.

실제 호출 구조를 줄인 예시
// core / ScenarioInterpreter
state = PlaybackState.COMPLETE
statementExecutor.runUntilYield(
    callStack = callStack,
    isEnded = { ended },
    shouldYield = {
        state != PlaybackState.COMPLETE
    },
    executeStatement = ::executeStatement,
)
엔진이 정하는 것: 문장을 실행하는 방법
게임이 정하는 것: 언제 사용자 입력을 기다릴지
게임의 선택지 처리 확인 ↗

예: 같은 격자라도 게임이 지정한 이동 비용에 따라 경로가 달라집니다.

1
게임이 지도 파일과 규격을 결정합니다.

HallPathGridLoader가 maps/pmaps/장면번호.json을 읽고 100×100인지 확인합니다. 엔진의 PathGrid는 임의의 양의 직사각형 크기를 받습니다.

2
게임이 비용을 지정합니다.

ScenarioStageMovementPlanner의 홀 설정은 기본 이동 1, 비어 있지 않은 지형 767, 점유 511, 방향 변경 15입니다. 이 숫자는 엔진에 내장되지 않습니다.

3
엔진이 결정적인 탐색 결과를 만듭니다.

GridPathfinder.find는 비용을 합산하여 좌표 목록을 돌려줍니다. blocked 셀은 통행 금지로 제거되는 대신 비용이 가산됩니다.

4
게임이 경로를 이동 연출로 바꿉니다.

게임의 이동 애니메이터가 좌표와 유닛을 연결하고 이동 시간·카메라·후속 스크립트를 처리합니다.

core / 게임이 소유하는 정책
PathCosts(
    step = 1,
    blocked = 767,
    occupied = 511,
    directionChange = 15,
)

가운데 갈색 지형을 지나는 비용만 바꿔 보세요. 알고리즘은 그대로입니다.

총 비용 53이동 8칸

설명용 7×5 격자 · 시작 S / 목표 G · 기본 이동 1 · 방향 변경 15 · 점유 부대 없음. 아래 데모는 Kotlin 엔진의 탐색 규칙을 JavaScript로 옮겨 보여 주며, 실제 게임 지도를 실행하는 것은 아닙니다.

예: “주군, 서두르셔야 합니다!”라는 문장을 누가 선택하고 누가 한 글자씩 공개할까요?

1
게임이 대사·번역·화자를 정합니다.

ScenarioDialogueTextCatalog가 줄 번호와 독립적인 고정 대사 ID를 해석합니다. 게임은 화자 이름, 초상화, 대화창 위치를 정합니다.

2
엔진이 시간에 따라 공개 범위를 진행합니다.

TextReveal은 원문과 시간을 받고 visibleText·isComplete를 제공합니다. 태그도 한 공개 단위로 처리하고 표시 문자열에서는 제거합니다.

3
게임이 클릭과 자동 진행의 의미를 정합니다.

전투·거리·궁전 모두 RuntimeDialogueSessionAdapter가 스크립트 상태를 변환하고, 하나의 DialogueSession이 첫 입력의 즉시 공개, 다음 입력의 대사 진행, 선택·모달·자동 닫기를 관리합니다. 전투는 시간 누적 방식과 공개 후 1초 자동 진행을, 시나리오는 콜백 타이머 방식을 사용합니다. 배치·자산은 장면별 설정으로 유지합니다.

4
게임이 자산과 모델을 렌더러에 넘깁니다.

한국어 글꼴 생성, JOJO_FONT_PATH, 번역 테이블과 자산의 해제 시점은 게임이 소유합니다.

4

그릴 이미지의 의미, 레이어 순서, 화면 전환과 dispose는 게임 화면·자원 소유자가 관리합니다.

06

검증된 범위와 현재의 한계

아래 수치는 엔진 분리 당시의 검증 기록입니다. 이후 고정 대사 ID·호스트 API 변경의 검증 범위와 현재 제약은 구현 현황에서 확인하세요.

24엔진 단위 테스트 통과
1,151게임 회귀 테스트 통과
59R 시나리오 기동·분기 진행
58S 전투 초기화·1턴 이벤트
✓데스크톱·Android·검증 모듈 컴파일
✓엔진 의존 경계 검사
✓영천 진행 경로·전투 데이터 적합성
✓검증된 헤드리스 경로에서 AST API 누락 없음
검증 명령
./gradlew :engine:test :core:test :desktop:classes \
  :android:compileDebugKotlin :verification:compileKotlin \
  :verification:verifyAllHeadless

시나리오는 59개 R 모듈의 기동과 한 입력 분기 진행을, 전투는 58개 S 모듈의 초기화와 1턴 이벤트를 확인했습니다. 전체 캠페인의 모든 분기 완주나 화면 픽셀 일치를 보장하는 결과는 아닙니다.

엔진 경계와 게임 내부 계층 정리는 별개입니다.

엔진은 게임을 참조하지 않도록 분리되어 있습니다. core 내부에는 아직 다음과 같은 결합이 남아 있습니다.

  • 일부 도메인 모델이 GameDataCatalog를 직접 참조합니다.
  • 일부 도메인 코드가 표시 문구를 참조합니다.
  • BattleScreen 같은 큰 화면 클래스는 추가 분리 대상입니다.

후속 작업에서는 게임 데이터의 읽기 전용 계약과 표시 모델을 나누고, 화면 상태의 실제 소유권에 맞추어 클래스를 분리합니다.

정리된 구형 실행 경로와 검증 전용 코드

현재 시나리오 실행은 ScenarioInterpreter와 엔진 AST 실행기로 통일했습니다. 사용하지 않던 ScenarioSource, ProgramPlayback, ScenarioPlayback, ScenarioProgramLoader, ScenarioScript·ScenarioTimeline 경로는 제거했습니다.

사용처가 없는 별도 대화 호스트·뷰와 옛 렌더러도 제거했습니다. 실제 선택지 ChoiceScene2dLayer는 계속 사용합니다. 옛 SDK 비교에만 쓰는 서비스·종료 화면 모형은 verification/fixtures/framework로 옮겨 게임 런타임에서 분리했습니다.
