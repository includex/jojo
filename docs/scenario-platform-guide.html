2. 대사 ID의 수명

기존 7,617개 대사에 R_00.scene1.dialogue0001 형식의 ID를 부여했습니다. module/scene 부분은 처음 만든 위치를 설명할 뿐, 현재 위치와 일치할 필요는 없습니다. 줄 삽입·함수 이름 변경·다른 모듈로 이동해도 ID를 그대로 가져갑니다. 번호를 다시 매기지 마세요.

stage.say('@dialogue:R_00.scene1.dialogue0001')

문장은 content/scenarios/dialogue-text.json의 entries에 있습니다. 문장을 고칠 때 ID는 유지합니다. 새로운 별도 대사에는 새 ID를 부여하고, 다른 대사에 기존 ID를 재사용하지 않습니다. 현재 검증은 호출 위치마다 유일한 ID를 요구합니다.

{
  "format": "jojo-scenario-dialogue-text/v1",
  "entries": {"R_01.scene1.recruit_greeting": "&512\n주군, 명을 내려주십시오."},
  "aliases": {},
  "legacyKeys": {}
}

위 JSON은 구조 설명용입니다. 실제 파일을 덮어쓰지 말고 entries에 항목만 추가합니다. \n은 JSON에서 줄바꿈을 나타냅니다. &512는 화자 512를 지정하는 기존 대사 형식이며 이 제어문법은 유지합니다. 대사 데이터는 YAML이 아닌 JSON입니다.

legacyKeys는 예전 R_00:scene1:줄번호 키를 고정 ID로 연결합니다. 과거 테스트·참조 호환용이며 신규 소스에는 쓰지 않습니다. aliases는 기존대로 별칭에서 실제 문자열을 찾습니다. ID를 삭제할 때는 이를 가리키는 legacyKeys도 검토해야 하므로 기존 대사의 제거는 호환성 변경으로 취급합니다.

3. 대사를 추가하는 순서

  1. 등록된 인물 ID를 확인합니다. 아래 예시는 YAML에 인물 512를 먼저 등록한 경우입니다.
  2. 카탈로그 전체에서 사용하지 않은 이름 R_01.scene1.recruit_greeting을 고릅니다. 허용 ID는 영문/숫자로 시작하고 영문·숫자·점·밑줄·하이픈을 사용합니다.
  3. entries에 위 예시의 문장 항목을 추가합니다. JSON 쉼표와 따옴표를 확인합니다.
  4. 실행되는 R_01의 scene 함수에 stage.say('@dialogue:R_01.scene1.recruit_greeting')를 넣습니다.
  5. 아래 검증을 실행합니다. 누락 ID, 중복 참조, 직접 쓴 대사, 참조되지 않은 entries는 빌드 오류입니다.
  6. 게임에서 화자·문장·첫 확인 시 전체 글자 공개·다음 확인 시 진행을 확인합니다.
python3 -m unittest tools.test_stable_dialogue_ids
./gradlew --no-daemon :core:exportScenarioAst :core:test
./gradlew --no-daemon :desktop:run --args="--scenario=R_01"

새 모듈은 manifest.json에도 등록합니다. 생성 AST는 수정하지 않습니다. 복원된 분기 보정에는 아직 외부 원본 assets가 필요합니다. 고정 ID는 대사 식별을 안정화하며, 모든 줄 번호 기반 검증 자료나 분기 보정 의존성을 제거하지는 않습니다.

4. 게임 명령 계약 v1

구현 위치: core/.../application/scenario/ScenarioHostApi.kt. ScenarioHostApiVersion.CURRENT = 1은 코드 계약 버전이며 실행 파일 간 버전 협상 프로토콜은 아닙니다.

명령입력과 효과재개 계약
say(text)@dialogue:ID를 카탈로그에서 해석. 미등록 ID는 즉시 오류. &로 시작하면 화자 대사, 아니면 정보 표시. 호스트는 기존 동적 호출 호환용 문자열도 허용하나 작성 소스 exporter는 고정 ID를 요구화면의 기존 대화 입력/자동 진행 완료 후 실행 재개
delay(ticks)1 tick = 0.1초. 음수는 0으로 처리. 원본의 첫 update 준비 단계를 유지기존 타이머 완료 후 재개. 단순 Thread.sleep으로 치환하면 타이밍이 달라짐
choice(options, portraitId, site)비어 있지 않은 선택지 문자열 목록과 선택적 초상화. 빈 목록은 상태 변경 전에 오류. site는 module/function/양수 line의 추적 정보CHOICE 상태로 대기. 기존 selectChoice/confirmChoice 경로로 확정
choiceResult새 선택지 대기 중 null, 확정 후 1부터 시작하는 번호로그의 option과 UI 선택 인덱스는 0부터 시작하므로 변환 필요
// Kotlin 호스트 계약 사용 예 (Lua 문법이 아님)
val api = interpreter.hostApi
api.choice(listOf("출진한다", "준비한다"), 0,
    ScenarioCallSite("R_01", "scene1", 60))
// 게임 입력으로 확정된 뒤:
val result = api.choiceResult // 첫 선택지는 1

이 API를 여러 명령을 한 번에 밀어 넣는 큐로 사용하지 않습니다. 어댑터는 대화·선택지·대기 상태를 확인하고 현재 명령 완료 후 다음 명령으로 진행해야 합니다. site.line은 추적용이며 대사 ID가 아닙니다.

5. Lua 전환 전 다음 단계

  1. 남은 stage/model/unit 호출을 상태 조회·상태 변경·연출 명령으로 나누고 타입과 오류 규칙을 정합니다.
  2. 입력/시간 대기와 재개를 독립 실행기 계약으로 추출합니다. Lua 코루틴이 중단될 지점과 선택 결과를 돌려주는 방식을 연결합니다.
  3. 변수 수명, 난수, 저장/불러오기, 실패 시 중단 정책을 정의합니다.
  4. 동일한 짧은 시나리오를 Python AST와 Lua로 실행해 대사 ID·선택 결과·게임 상태·시간 흐름을 비교한 뒤 범위를 넓힙니다.
