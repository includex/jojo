어디에, 어떻게 추가할까요?

인물·거리와 궁전 대화·전투·아이템·책략·스킬을 추가할 때 따라가는 실무 가이드입니다. 현재의 데이터 입력, 실행 경로, 엔진 API와 검증 기준을 함께 설명합니다.

콘텐츠와 규칙 → core범용 실행 기능 → engine구조부터 살펴보기 ↗

검색어가 포함된 장만 표시합니다.

01　먼저 수정할 영역을 고릅니다

새 인물·아이템·책략·장면은 대부분 :core의 콘텐츠와 게임 규칙을 확장하는 작업입니다. 기존 실행 기능으로 표현할 수 있으면 엔진을 수정하지 않습니다. “독립 엔진”은 콘텐츠 편집기나 플러그인 등록 시스템을 뜻하지 않습니다.

추가할 기능주로 바꾸는 곳엔진 수정이 필요한 경우
인물unit 테이블 → 카탈로그 → 캠페인 합류·전투 배치 → 초상화·스프라이트일반적으로 없음
거리·궁전 대화R 모듈·대사 카탈로그·배경·장면 전환지원하지 않는 일반 AST 문법이 꼭 필요할 때
전투S 모듈·전장 자산·부대 배치·승패·복귀 경로범용 탐색 알고리즘 자체를 확장할 때
아이템item/itemSkills/shop 테이블·인벤토리·장비·획득/소비일반적으로 없음
책략·스킬magic/defineSkill 등 테이블·대상/효과 규칙·AI·연출일반적으로 없음
새 stage.* 명령core의 호스트 디스패처·무대 상태·연출 완료 신호명령 이름을 엔진에 넣지 않음
모듈과 계층

desktop / android → core → engine. core 안에서는 domain에 규칙, application에 실행 순서와 스크립트 연결, infrastructure에 파일·저장·번역, presentation에 화면·입력·자원 수명을 둡니다. 게임 규칙을 새로 추가할 때 큰 BattleScreen의 분기부터 늘리지 말고, 규칙과 결과를 먼저 분리합니다.

02　원본과 생성물을 구분합니다

인물·아이템·스킬은 이제 저장소의 content/ 아래 항목별 YAML이 작성 원본입니다. 다른 맵·이미지·병종·시나리오 등은 기존 외부 복원 프로젝트의 입력을 사용합니다.

작성·수정하는 원본
content/*.yaml · Python · manifest · 이미지
↓ 내보내기
core/build/generated/
game-content · scenario-ast · map-assets 등
↓ :core:processResources
번들 리소스 → core 런타임
카탈로그 · 규칙 · 화면
대상현재 입력생성·사용 경로
시나리오외부 sgccz-desktop/decompiled-python/*.py, manifest.jsongenerated/scenario-ast → scenario-ast/*.json, Python/manifest → scenarios/
인물·아이템·스킬content/characters, content/equipment, content/skills/{active,passive,assignments,equipment}의 YAML:core:compileGameContent → generated/game-content/data/*.bin → maps/data/
기타 테이블·맵 자산외부 sgccz-desktop/assets의 원본 asset 데이터generated/map-assets → maps/. YAML로 옮긴 여섯 표는 여기서 번들하지 않습니다.

작성 규칙과 ID

요소 하나를 YAML 파일 하나로 정의합니다. 이름 있는 필드·타입은 content/schema.json을 따릅니다. 각 디렉토리의 ID는 0부터 연속되며 새 항목은 마지막 다음 ID로 추가합니다. 기존 ID를 바꾸면 세이브와 스크립트의 참조 의미가 달라집니다. 중복 ID/필드, 빠진 ID, 알 수 없는 필드, 타입 오류와 주요 스킬 참조 오류는 빌드에서 실패합니다.

빌드가 생성한 core/build/generated/game-content는 편집하지 않습니다. content/를 Git에 포함하면 이 여섯 테이블의 수정은 저장소 안에서 관리됩니다. YAML 파서는 빌드 도구에만 있고 실제 게임은 기존 테이블 형식을 읽습니다.

콘텐츠 편집 상세 안내 ↗ 필드 스키마 ↗
아직 외부 입력인 영역

기타 테이블·이미지·Python 시나리오는 core/build.gradle.kts의 외부 경로를 사용합니다. 이 영역을 수정한 내용은 현재 저장소 커밋에 자동 포함되지 않습니다. YAML로 새 인물과 장비를 정의해도 필요한 자산과 게임 규칙을 별도로 연결해야 합니다. 소비 아이템의 ID 범위 등 기존 게임 제약도 그대로입니다.

./gradlew :core:compileGameContent :core:processResources

입력 경로와 패키징 규칙: build.gradle.kts ↗ export_python_ast.py ↗ export_map_assets.py ↗

03　신규 인물 추가

작성 위치: content/characters/0000.yaml부터 실제 예제를 확인하세요. 새 요소는 같은 형식으로 정의하고 :core:compileGameContent로 검증합니다.

목표 예: 새 장수를 캠페인에 합류시키고, 거리에서는 말하게 하고, 전투에서는 이동·공격하게 합니다. 이름 한 줄을 추가하는 작업과 전투 가능한 장수를 추가하는 작업의 범위가 다릅니다.

  1. 안정적인 인물 ID와 테이블 행을 정합니다. unit.bin은 YAML에서 생성하는 배열 기반 테이블입니다. 기존 인덱스를 이동·재사용하면 저장 데이터와 시나리오 참조의 의미가 바뀝니다. 인물·배치 인덱스·초상화 ID를 같은 값으로 가정하지 마세요.
  2. 기존 스키마를 따라 기본 능력과 병종을 채웁니다. GameDataCatalogUnitDomain.unitProfile(id) 기준 주요 필드는 아래와 같습니다. 새 필드가 필요하면 원본 → repository/bundle → catalog/profile → 소비 규칙까지 전달합니다.
unit 행 필드의미함께 확인할 참조
0 / 1 / 2 / 14 / 21이름 / face / mapAvatar / battleAvatar / battleAvatarType한국어·초상화·거리/전투 스프라이트
4~8 / 9~10기본 능력 / HP·MP성장·전투 프로필 계산
11 / 12 / 19posts / level / famous병종·책략 습득·초기 레벨
  1. 화면 자산을 연결합니다. 내보내기가 maps/heads, maps/hall-units, maps/units/{mov,mov2,atk,atk2,spc,spc2}에 실제 새 자산을 생성하는지 확인합니다. 파일 존재뿐 아니라 ID 변환·프레임·방향 규칙도 맞춰야 합니다. 전투 초상화에는 face에서 변환한 값을 사용하는 경로가 있습니다.
  2. 합류와 배치를 각각 연결합니다. 기존 스크립트 호스트 명령 model.unitJoin은 ScenarioStageBattleSetup.joinUnit으로 이어져 캠페인 합류와 기본 장비를 반영합니다. 거리의 stage.showUnits, 전투의 생성/배치 데이터는 별도입니다. 화면에 등장했다고 캠페인 합류가 완료되는 것은 아닙니다.
  3. 저장과 UI를 확인합니다. 새 인물을 포함해 저장·불러오기, 장비 변경, 인물 목록, 능력창, 사용 가능한 책략을 확인합니다. 기존 세이브의 ID 참조를 보존합니다.

완료 기준: 카탈로그 조회 → 합류 → 장비 → 거리 대사 → 전투 배치 → 저장 후 복원까지 같은 인물 ID로 연결됩니다.

GameDataCatalogUnitDomain.kt ↗ScenarioStageBattleSetup.kt ↗ScenarioStageBattleUnitFactory.kt ↗CampaignRuntimeStateCodec.kt ↗GameDataRepositoryTest.kt ↗

04　길거리·궁전 대화 장면 추가

새 화면 클래스를 만들기 전에 기존 R 모듈의 scene0, scene1 등으로 표현합니다. 거리·궁전은 시나리오 화면과 공통 대화 렌더러를 사용하며 배경·유닛·진행 설정으로 구성합니다.

  1. 기존 모듈에 장면을 넣을지, R 모듈을 새로 만들지 정합니다. ScenarioNavigationCoordinator는 조건이 맞으면 다음 sceneN 함수를 순서대로 시작합니다. 거점 메뉴가 열려 있거나 명시적 점프가 있는 경우는 별도 전환 경로입니다.
  2. 배경과 화자를 배치한 뒤 대사를 작성합니다. 아래는 R_01의 기존 호출 형태를 따르는 작성 예입니다. 배경/인물 ID는 예시의 기존 자원을 사용한 값이며 새 ID 등록을 대신하지 않습니다.
def scene1():
    stage.loadBg(2, 9)
    stage.showUnits([[192, 52, 41, 2]])
    stage.draw()
    stage.setStageName('낙양@승상부')
    stage.say('&192\n주군, 서두르셔야 합니다.')
    return False

showUnits 항목은 [인물 ID, x, y, 방향] 형태이며 &ID 는 화자 구분입니다. loadBg의 인자 의미는 R/S 모듈에 따라 다르므로 전투 호출 형태를 그대로 복사하지 않습니다. 장면 대사는 일반 위젯을 직접 띄우지 않고 스크립트의 입력 대기 상태를 거쳐 표시합니다.

  1. 신규 모듈은 manifest에도 등록합니다. AST exporter는 *.py를 찾지만 manifest를 자동 갱신하지 않습니다. ScenarioCatalog는 manifest를 열거하므로 “AST 파일은 있는데 시나리오 목록에 없음” 상태를 구분해야 합니다. 현재 파서는 manifest의 들여쓰기 형식까지 가정하므로 기존 형식을 유지합니다.
  2. 대사 카탈로그 키를 맞춥니다. exporter는 리터럴 stage.say를 @dialogue:모듈:함수:원본줄번호로 바꿉니다. 생성된 AST의 키를 확인해 dialogue-text.json의 entries에 등록하세요. Python에 문장을 썼다는 이유만으로 런타임 카탈로그가 자동 생성되지는 않습니다. 키가 없으면 예외가 납니다.
  3. 줄 이동과 분기 입력을 검증합니다. 파일 위쪽에 줄을 삽입하면 기존 대사 키도 달라질 수 있습니다. 기존 키의 문장과 새 키의 문장이 대응하는지 확인합니다. 선택지는 지원되는 stage.choice/stage.ask 기존 패턴을 따르고, 선택 결과가 다음 문장부터 재개되는지 확인합니다.
  4. 장면 배치만 조정합니다. RuntimeDialogueSessionAdapter → DialogueSession → DialogueRenderer가 대사·선택·모달의 공통 경로입니다. 시나리오의 좌우/상하 배치는 ScenarioDialoguePlacementPolicy로 결정합니다. 새 장면마다 글자 공개·확인 입력·자동 닫기를 재구현하지 않습니다.
# 실제로 번들된 기존 모듈 실행 예; 새 모듈은 등록 후 ID를 바꿉니다.
./gradlew :desktop:run --args="--scenario=R_01"
완료 기준

모든 화자·초상화 표시, 긴 한국어 문장 줄바꿈, 첫 확인의 전체 공개와 다음 확인의 진행, 좌우/상단 배치, 선택지 각 분기, 자동 진행, 다음 장면/전투 전환을 확인합니다. 대사 검증은 새 S 전투의 대사에도 동일하게 적용합니다.

ScenarioCatalog.kt ↗ScenarioDialogueTextCatalog.kt ↗ScenarioNavigationCoordinator.kt ↗RuntimeDialogueSessionAdapter.kt ↗ScenarioDialoguePlacementPolicy.kt ↗ScenarioPlaybackControllerTest.kt ↗

05　신규 전투 장면 추가

전투는 S_XX 모듈을 중심으로 조립합니다. 전장 배경만 추가하는 것으로는 부대·전술 지형·턴 이벤트·승패 처리가 구성되지 않습니다.

scene0
초기화·전장·부대·승리 조건
↓ 전투 실행
scene1
턴·진영·조건에 따른 이벤트
↓ 승패 확정
scene2
종료 대사·보상·이탈/복귀
  1. 기존 S 모듈의 계약을 복제합니다. S_00 등에서 stage.initFight, stage.setGlobalData, stage.createFriend, stage.createEnemy, stage.setWinCondition 및 __dispatch__ 흐름을 함께 확인합니다. 인자의 의미를 확인하지 않고 초기화 부분만 삭제하면 실행 순서가 달라집니다.
  2. 전장 이미지와 전술 지형을 함께 준비합니다. 이미지 크기, 지형 데이터, 병종별 이동/공격 범위, 배치 좌표를 맞춥니다. 거리 이동의 홀 100×100 격자와 전투의 지형·이동 판정은 같은 규칙이 아닙니다. GridPathfinder에 임의 전투 지형을 바로 넘겨 전투 규칙을 대체하지 않습니다.
  3. 배치 키와 데이터 참조를 확인합니다. ScenarioStageBattleUnitFactory가 읽는 id, idx, lv, x, y 등의 계약을 기준으로 인물·부대 인스턴스·초기 능력·진영을 구성합니다. 캠페인 아군과 스크립트 생성 부대의 소유권을 구분합니다.
  4. 턴 이벤트와 종료 흐름을 연결합니다. 이벤트가 매 프레임 반복되지 않도록 기존 변수/조건 패턴을 따릅니다. 승리·패배·전투 중 대사·전투 뒤 대사·보상 반영을 각각 검증합니다. BattleScenarioFactory/BattleScenarioAssembler는 스크립트 부대를 실제 전투 상태로 만드는 경로입니다.
  5. R→S→R 전환을 지정합니다. 현재 일반 진입은 R_XX와 같은 번호의 S_XX를 찾고, 없으면 S_00으로 돌아가는 경로가 있습니다. jumpScene은 짝수 R/홀수 S 번호 매핑을 사용합니다. 새 모듈이 의도한 전투로 연결되는지 실제 대상 ID를 확인하세요.
  6. 카탈로그와 세이브 복귀도 확인합니다. 신규 S 모듈 manifest·대사 키 등록을 수행하고, 전투 종료 후 다음 R 모듈이나 명시한 복귀 지점이 존재하는지 확인합니다. 전투 중 저장을 제공한다면 이벤트 변수와 캠페인 상태 복원도 검사합니다.
# 기존 기본 전투에 직접 진입하고 R_01로 복귀하는 실행 예
./gradlew :desktop:run --args="--battle --battle-return=R_01"
# 신규 전투는 먼저 등록된 R 모듈에서 연결 경로를 통해 실행해 확인합니다.

완료 기준: 새 전투의 올바른 맵·진영·인물·장비, 첫 턴 이벤트, 이동/공격/책략, 승패 양쪽 종료 경로, 보상 중복 방지, 복귀를 확인합니다. 전체 카탈로그 기동 검증은 모든 턴과 분기의 완주 검증을 대신하지 않습니다.

06　신규 아이템 추가

  1. 기존 효과 조합인지 새 규칙인지 나눕니다. 능력치·회복량·가격만 다른 아이템은 기존 데이터 흐름을 따릅니다. “공격 후 특정 상태를 전파한다” 같은 새 효과라면 domain 규칙, 결과 반영과 연출도 추가해야 합니다.
  2. YAML과 스킬 연결을 작성합니다. content/equipment/0026.yaml의 skillEffects는 content/skills/equipment의 효과 ID 목록입니다. 이름·가격·아이콘·값은 같은 YAML에 작성합니다. 현재 equipmentProfile의 필드 해석은 아래와 같습니다. “아이템 ID”와 “아이콘 번호”를 구분하세요.

  2. 소지 유형과 저장을 확인합니다. 아래 ID 제약에 해당하면 단순 행 추가 범위를 넘습니다. 장착·해제·소모·수량·경험치·강화·저장을 해당 종류에 맞게 검증합니다.
  3. 아이콘·설명·능력창을 확인합니다. maps/item-icons에 해당 파일이 내보내지고 장비창·상점·획득 안내·보물창에서 같은 항목이 보이는지 확인합니다.

07　책략과 패시브 스킬 추가

작성 위치: content/skills/active는 책략, passive는 효과 정의, assignments는 인물·병종 배정, equipment는 장비 효과·성장 정의입니다. 책략 예제와 장비 효과 예제를 참고하세요.

이 프로젝트의 “스킬”은 단일 목록이 아닙니다. 먼저 능동 책략, 인물/병종 패시브, 장비 특수 능력 중 무엇인지 정합니다.

종류데이터 입구실제 동작 경로
능동 책략magic, hitarea, effarea프로필·습득 목록 → 대상 선택 → MP/환경/효과 판정 → 상태 변경 → 연출
인물·병종 패시브defineSkill, unitPostsSkillskillsForUnit → passiveAbility/mergeSkills → 실제 전투 규칙
장비 특수 능력itemSkills + item장착 → equipmentSkills → 패시브 합성 → 전투 반영

능동 책략

  1. magic 스키마를 작성합니다. 주요 필드는 0 name, 1 type, 2 target, 3 hitArea, 4 effectArea, 5 MP, 6 icon, 7 intro, 8 effect, 9 power, 10 harmType, 11 condition, 12 aiUse, 13 hitRateLimit, 14 category입니다. 15번 필드는 병종 ID별 습득 레벨을 연결합니다. 범위 참조는 hitarea/effarea 데이터와 맞춰야 합니다.
  2. 습득·표시까지 연결합니다. learnedMagicIds, BattleUnitMagicProjector, 캠페인의 extraMagic 경로를 확인합니다. 데이터 행만 추가해도 모든 인물에게 자동 노출되는 것은 아닙니다.
  3. 효과가 이미 지원되는지 확인합니다. MagicResolver와 MagicDamageCalculator에는 category·특정 ID·날씨 등 조건 분기가 남아 있습니다. 새 category는 테이블만 추가해 처리된다고 가정하지 않습니다. 대상/사거리·명중/저항·MP·피해/회복·상태·사망 처리에 필요한 규칙을 core domain에 추가합니다.
  4. AI와 연출을 연결합니다. 사용 조건과 AI 선택 여부를 검증하고 MagicEffectCatalog, BattleMagicPresentationPlanner 및 maps/magic-icons, maps/effects 자산을 확인합니다. 논리 효과 적용과 화면 연출 완료 시점을 구분합니다.

패시브·장비 스킬

defineSkill의 name, incType, arg와 배정 테이블을 확인합니다. passiveAbility/mergeSkills가 해석하는 범위 안이면 데이터 조합으로 추가하고, 새로운 효과라면 그 값을 소비하는 전투 규칙까지 확장합니다. 설명 문구만 추가하면 전투 효과는 생기지 않습니다. 중복 장착·동일 계열 스킬의 합산/최댓값 규칙과 임시 버프 해제도 검사합니다.

완료 기준: 습득 조건, 목록/설명/아이콘, 아군·적군·빈 칸 대상 판정, MP 부족, 범위 경계, 상태 저항, AI, 효과 연출, 저장 후 습득/장착 유지가 확인되어야 합니다. 난수를 쓰는 규칙 테스트는 제어 가능한 입력으로 작성합니다.

08　엔진 API를 사용하는 방법

게임 입력과 정책은 core가 만들고 엔진에는 값과 콜백으로 전달합니다. 아래 Kotlin 예제는 현재 공개 API를 사용합니다. 실제 게임 자산·캠페인 상태와 연결하는 코드는 core에 둡니다.

가중 격자 경로 탐색

import com.jojo.engine.pathfinding.GridPathfinder
import com.jojo.engine.pathfinding.PathCosts
import com.jojo.engine.pathfinding.PathGrid

val grid = PathGrid.open(width = 7, height = 5)
val path = GridPathfinder.find(
    startX = 0, startY = 2, targetX = 6, targetY = 2,
    grid = grid,
    occupied = emptySet(),
    costs = PathCosts(step = 1, blocked = 767, occupied = 511, directionChange = 15),
)
// path는 시작·목표 좌표를 포함합니다. 격자 밖 좌표 요청은 null입니다.

PathGrid는 양수 크기의 직사각형을 받습니다. 0이 아닌 지형은 추가 비용을 부과하는 칸이며 절대 통과 불가를 뜻하지 않습니다. 비용의 의미, 점유 목록, 게임의 이동 가능 판정은 core가 정합니다. 홀의 100×100 제한은 core 로더/이동 정책에 있습니다.

일반 텍스트 공개

import com.jojo.engine.text.TextReveal
import com.jojo.engine.text.RevealTiming

val reveal = TextReveal(
    characterIntervalSeconds = 0.04f,
    timing = RevealTiming.ACCUMULATING,
)
reveal.setSource("주군, 서두르셔야 합니다.")
reveal.update(0.12f)
val visible = reveal.visibleText
val complete = reveal.isComplete
reveal.revealAllIfPending()
reveal.reset()

새 설명창·로그 같은 독립 텍스트 효과에는 이 API를 쓸 수 있습니다. 기존 대화 장면은 직접 TextReveal을 추가하지 말고 공통 DialogueSession을 사용합니다. 확인 입력·선택지·모달·자동 진행은 엔진의 책임이 아닙니다. 콜백 타이머 방식은 첫 update를 초기화에 사용하고 프레임당 공개 단위가 달라집니다.

09　추가 완료를 판단하는 순서

먼저 새 기능의 좁은 동작을 확인한 뒤, 모듈 컴파일과 전체 기동 검증으로 범위를 넓힙니다. UI가 떴다는 사실과 규칙·저장·장면 복귀가 맞는지는 별개로 확인합니다.

  1. 데이터: 새 ID·필수 필드·참조 테이블·번역 키·자산이 실제 번들에 있는지 확인합니다. ID 인덱스를 바꿨다면 모든 참조와 세이브 변환을 검토합니다.
  2. 규칙: 대상·범위 경계·비용 부족·실패/성공·중복 적용·해제 조건을 테스트합니다. 엔진 알고리즘은 engine에서, 게임 의미는 core에서 검증합니다.
  3. 화면: 실제 신규 R/S 모듈을 실행해 한국어 줄바꿈·입력·대화 진행·효과·장면 복귀를 확인합니다. verification의 캡처/fixture가 프로덕션을 대신하게 만들지 않습니다.
  4. 저장: 새 인물·아이템·습득 스킬·진행 변수를 저장하고 복원합니다. 과거 세이브의 기존 항목 의미를 보존합니다.
  5. 통합: 아래 빌드와 카탈로그 검증을 실행하고, 새 시나리오가 실제로 목록에 포함되었는지 출력과 카탈로그를 확인합니다. 전체 기동 통과를 모든 전투/분기 완주로 해석하지 않습니다.
# 좁은 테스트 예 (새 기능 테스트도 같은 방식으로 지정)
./gradlew :core:test --tests 'com.jojo.game.RuntimeDialogueSessionAdapterTest'
./gradlew :core:test --tests 'com.jojo.game.MagicResolverTest'

# 엔진·게임 테스트와 모든 호출 모듈 컴파일
./gradlew :engine:test :core:test :desktop:classes :android:compileDebugKotlin :verification:compileKotlin

# 시나리오/전투 카탈로그·영천 경로·AST API 검증
./gradlew :verification:verifyAllHeadless

# 캠페인 흐름까지 변경했다면 추가 실행
./gradlew :verification:campaignE2e
기존 콘텐츠의 기준과 신규 콘텐츠의 기준을 분리합니다.

현재 테스트와 비교 도구에는 원본 콘텐츠 수·ID·정확한 표/화면을 전제로 한 검사가 있습니다. 신규 행 때문에 실패했다면 원본 회귀를 지우지 말고 “기존 콘텐츠 동일성”과 “신규 콘텐츠의 의도한 동작”을 구분해 검증 범위를 조정합니다. 프로덕션의 --verify* 인자는 제거되어 있으므로 위의 독립 verification 작업을 사용합니다.

여러 기능이 묶인 개발 예

“새 장수가 거리에서 합류하고, 새 전투에서 보물과 책략을 얻는다”면 인물 ID/자산 → 아이템·책략 데이터/규칙 → R 대사·합류 → S 배치·이벤트·승패·보상 → 복귀·저장 순으로 연결합니다. 단계마다 카탈로그와 규칙을 검증한 뒤 화면에 연결하면, 문제 발생 시 데이터·실행·표시 중 어디가 끊겼는지 구분할 수 있습니다.

엔진/코어 이용 가이드의 범위: 이 문서는 현재 코드의 확장 지점을 설명합니다. 인물·아이템·스킬은 개별 YAML로 정의하고 빌드가 검증·변환합니다. 시각적 콘텐츠 편집기나 자동 ID 할당 기능은 제공하지 않습니다. 나머지 콘텐츠의 외부 입력 구조는 02를 따릅니다.
