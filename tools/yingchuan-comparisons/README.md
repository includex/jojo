# 영천전투 구간 대조 스크립트

각 스크립트는 원본과 포트의 full trace를 받아 **같은 검사를 양쪽에 돌리고 결과가 같은지**
본다. `python3 <script>.py <source-trace.json> <port-trace.json>` 형태이며 JSON을 표준출력에
낸다. 포트 trace 대신 원본 trace를 두 번 주면 **자기검사**가 되고, 스크립트를 새로 쓰거나
고친 뒤에는 반드시 먼저 이것을 통과시킨다. 이 절차가 2026-09-20 세션에서 검사 오류를 세 번
걸렀다(유닛의 시작 HP 가정, 조조의 시작 위치 가정, 유닛의 첫 행동 구간 오인).

## 구간과 실행 명령

원본은 `tools/capture_yingchuan_source_walkthrough.cjs`, 포트는
`:verification:captureYingchuanWalkthrough`로 뜬다. 모드 이름이 양쪽에서 **다를 수 있다**.

| 스크립트 | 원본 모드 / 상한(ms) | 포트 모드 / `maxSimSeconds` |
| --- | --- | --- |
| `first-combat.py` | `first-normal-combat` 45000 | 같음 / 기본 |
| `next-actions.py` | `next-normal-actions` 60000 | 같음 / **60** |
| `enemy-first.py` | `enemy-first-combat` 60000 | 같음 / 60 |
| `477.py` | `477-settlement-order` 60000 | **`enemy-settlement`** / 60 |
| `first-round-end.py` | `first-round-end` 90000 | 같음 / 90 |
| `round2-handoff.py` | `round2-handoff` 150000 | 같음 / 150 |
| `single-action.py` | `single-player-action` 180000 | 같음 / 180 |
| `round2-followup.py` | `round2-followup` 180000 | 같음 / 180 |
| `round2-fc.py` | `round2-first-combat` 180000 | 같음 / 180 |
| `round3-fc.py` | `round3-first-combat` 210000 | 같음 / 210 |
| `round3-fu.py` | `round3-followup` 210000 | 같음 / 210 |
| `round3-ca.py` | `round3-counterattack` 240000 | 같음 / 240 |
| `round3-210.py`, `round3-210-death.py` | `round3-210` 300000 | 같음 / 300 |

포트 trace는 출력 디렉터리의 `yingchuan-manual-trace.json`, 원본은 `source-full-trace.json`이다.
**포트의 기본 시뮬레이션 시간은 30초라 대부분의 구간을 잘라 먹는다.** 위 표의 값을 반드시 준다.

## 판정 규칙과 그 근거

`allPass`는 "동일"이 아니라 **"회귀 없음"**을 뜻한다. 다음은 값을 드러내되 판정하지 않으며,
각 스크립트의 주석에 근거가 있다.

- **애니메이션 길이는 클립 시계로 본다.** trace의 유닛 tuple **인덱스 15**가
  `cc.AnimationState.time`이다. 원본의 wall 시각에는 캡처 pacing이 섞인다. 퇴각(`anime23`)은
  자산 길이 30/24 = 1.25초이며 양쪽 모두 그 값에서 숨긴다.
- **정산 지속 시간은 타이머 양자화 차이를 갖는다.** 원본은 `scheduleOnce`/`schedule`을 여럿
  쌓아 쓰고(패널 하나에 7개, MINE+OTHER면 16개) Cocos `CCTimer`가 초과분을 버려 조금씩
  늘어난다. 포트는 절대 마감을 쓴다. 예산은 항목별로 같다.
- **조작기 입력을 낀 간격은 비교 대상이 아니다.** 원본은 CDP 포인터, 포트는 자체
  InputProcessor다. AI가 구동하는 이동→공격은 여섯 구간에서 0.29~0.32초로 모이는 반면
  조작기 구간은 0.77~3.37초로 흩어진다.
- **정체 프레임은 타이머 구동 구간만 부풀린다.** 창 안의 `dt > 0.05`를 검출하되, 클립이
  구동하는 창은 정체 동안 클립도 함께 진행하므로 제외하지 않는다. 그러지 않으면 캡처가
  촘촘한 모드에서 판정력이 사라진다.

## 차이를 발견했을 때

이 순서를 지킨다. 2026-09-20 세션에서 이 순서를 건너뛰어 **다섯 번** 존재하지 않는 포트
결함을 보고할 뻔했다.

1. **애니메이션 길이인가?** 인덱스 15의 클립 시계로 다시 잰다.
2. **원본을 두 번 돌려 그 지표의 자체 편차를 잰다.** 어떤 지표는 원본이 스스로 0.278초
   흔들린다.
3. **편차가 좁아도 안심하지 않는다.** 캡처는 같은 의미 지점에서 찍히므로 오염이 **결정적**
   이다. 매 실행 같은 창을 같은 크기로 부풀린다. 대신 **같은 실행 안의 동종 측정과 비교**
   한다. 예: 한 구간의 대사 셋 중 둘이 글자당 0.055~0.058초인데 하나만 0.173초면 그 하나가
   이상값이다.
4. **"클립이 dt만큼 진행하니 면역"은 창의 끝이 그 클립의 완료일 때만 참이다.** 끝이 타이머나
   대사 닫힘이면 정체의 dt가 그대로 더해진다.
5. **기대값을 판정 대상과 같은 쌍에서 계산하지 않는다.** 순환이며 항상 맞는다.
6. **경계를 찾지 못하면 통과가 아니라 실패다.** 스크립트가 `StopIteration`으로 멈추게 둔다.
   관측하지 못한 것을 조용히 건너뛰면 없는 합격이 만들어진다.

## 한쪽씩의 검사로는 부족하다

각 스크립트는 상태 검사와 **교차 타이밍 델타**를 함께 본다. 2026-09-20 이전에는 한쪽씩의
검사만 있었고, 그 상태에서 14개 검사가 양쪽 모두 통과하면서 **1.63초짜리 완료 자세 오차**를
놓쳤다. 각 진영이 자기 자신과는 일관됐기 때문이다.
